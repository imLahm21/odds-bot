## 3. 工作包

### WP-1 全模型调用改流式（V11、V12、V13）

1. **`bot/llm_client.py` 新增** `collect_model(...) -> str`，契约与 `chat_model` 相同（成功返回正文，失败返回以「LLM 请求失败」等既有前缀开头的错误串，不抛异常）：

   ```python
   def collect_model(system, user, model, effort="", max_tokens=0,
                     input_metrics=None, route_group="", cancel=None) -> str
   ```

   - 内部迭代 `stream_chat_model(system, user, model=model, effort=effort, max_tokens=max_tokens, input_metrics=input_metrics, route_group=route_group)`，**不传** `fallback_models`（逐模型的回退由调用方负责）。
   - 事件处理：`delta` 记下最新累积文本；`done` 返回 `payload.strip()`；`error` 返回 `payload`（若不以既有错误前缀开头，包成 `"LLM 请求失败（…）"`）；`queued` / `warning` 忽略。
   - 每收到一个事件检查 `cancel`：已置位就 `close()` 生成器并返回 `"LLM 请求失败（已取消）"`。
   - 已有部分正文后出错同样按失败返回——全模型的中间产物不展示给用户，可以安全换模型重来。
   - 流式路径下读超时不会在同端点重试（`_stream_one` 只重试 429 / 5xx），所以不需要改 `_do_chat`。

2. **`multi_analyzer._call_route`**：把 `llm_client.chat_model(...)` 换成 `llm_client.collect_model(..., cancel=cancel)`，去掉 `timeout=config.FULL_CONSULT_TIMEOUT`。
   - 新增总时限：循环开始前记 `started = time.monotonic()`；进入下一个候选前若 `time.monotonic() - started > config.FULL_CONSULT_ROLE_DEADLINE`，
     把剩余候选记为 `{"status": "skipped", "error": "超过职责总时限"}` 并跳出。

3. **`multi_analyzer._stream_report`**（合并）：改成逐个候选调用。
   - 候选顺序：`_route_candidates(spec)` 的全部项，其后接公共兜底（如已配置）。
   - 对每个候选调用 `stream_chat_model(..., fallback_models=())`（兜底带 `route_group`），沿用现有的 `progress(stage)`、`cancel` 检查和 `trace` 更新。
   - 任何 `error`（不论是否已有部分正文）→ 记 `trace["partial_output"] = True`（仅当确有部分正文时），继续下一个候选。
   - 删除「已有部分正文就 `return ""`」和 `rescue_skipped_reason = "partial_output"` 的逻辑。
   - 同样受 `FULL_CONSULT_ROLE_DEADLINE` 约束。

4. **测试迁移**：`tests/` 里共有 43 处对 `llm_client.chat_model` 的 patch 或断言，凡是经由 `multi_analyzer` 触发的都改为 patch `llm_client.collect_model`（返回值类型相同，都是 `str`）。`chat_model` 本身保留，直接测它的用例不动。

### WP-5 审计与修复（V7~V10）

1. **审计输入 `_audit_input`** 追加两段（来自 `bundle`）：`### 代码计算的市场事实与已触发假设`、`### 代码候选表`。

2. **确定性检查 `_basic_report_issues`** 新增（都算阻断项），签名加 `bundle: dict | None = None`：
   - 第 7 节缺「信号强度」行或「数据质量」行：用 `typesafe_decisions.parse_signal_strength(report) is None`、`parse_data_quality(report) is None` 判定。
   - 第 8 节候选表无法解析：`typesafe_decisions._selection_pool(report) is None`。
   - 信号强度越权：解析出的信号强度为 `medium` / `strong` 且 `verified_hypothesis_count() == 0`。
   - 候选表与代码候选表不一致（`bundle` 非空时）：新函数 `_candidate_mismatches(report, bundle) -> list[str]`：
     - `table = candidates.build_table(csv_text, league, home, away)`；为 `None` 时返回空列表。
     - 报告行取 `_selection_pool(report)` 的候选，按顺序与 `table.rows` 的前 N 行逐行比（N = 代码表行数）。
     - 赔率差 > 0.005，或 edge 都有数值且相差 > 0.002（0.2 个百分点）→ 记一条 `"C03 赔率 1.95≠1.92"` 这样的短说明。
     - 报告行数少于代码表行数 → 记 `"候选表缺 N 行"`。模型在表末追加的行（主 / 客队大小球）不比。
     - 有不一致时 `_basic_report_issues` 加一条 `"第 8 节候选表与代码候选表不一致：" + "；".join(前 5 条)`。
   - 复盘的 `_basic_review_issues` 不加这些。

3. **审计提示词与严重度**：`_audit_report` 的 system 改为要求每条 issue 带 `severity`：

   ```
   {"ok":true,"issues":[{"section":"7","severity":"blocker","problem":"...","required_fix":"..."}]}
   severity 只能是 blocker 或 minor。blocker 仅限：缺少必需章节；无已验证假设且无基本面明文覆盖却给出方向；
   第 7 节各判定互相矛盾（如判小球却预测 3:2）；第 8 节数字与代码候选表不一致；有侧重但第 9 节未回应。
   措辞、详略、可读性问题一律 minor。拿不准时标 minor。
   ```

   返回值结构改为：

   ```python
   {"ok": bool, "issues": [...全部...], "blockers": [...确定性问题 + severity==blocker 的...],
    "minors": [...], "route": route}
   ```

   - `ok = not blockers`（`minor` 不影响 `ok`；模型返回 `ok=false` 但没有 blocker 时也算通过）。
   - 确定性问题统一包成 `{"section": "", "severity": "blocker", "problem": 文本}` 再并入。
   - 没有 `severity` 字段的旧式返回按 `minor` 处理。
   - `_review_audit` 同样加 `severity` 与 `blockers` / `minors`，规则相同（复盘的 blocker：缺章节、改写了盲推、结算算错）。

4. **修复**（`run()` 里 `if not audit["ok"]` 那段，`run_review()` 同理）：
   - 只把 `audit["blockers"]` 交给修复模型。
   - 修复的 user 输入追加 `bundle["market_block"]`、`bundle["candidates_block"]`，system 追加：
     `第 8 节候选表的行与数字必须与「代码候选表」逐字一致；只改被指出的问题，其余原样保留。`
   - **验收后才替换**（V9）。新函数 `_accept_repair(original, repaired, bundle) -> bool`，全部满足才接受：
     - `len(repaired) >= FULL_CONSULT_REPAIR_MIN_RATIO * len(original)`；
     - `len(_basic_report_issues(repaired, ..., bundle=bundle)) <= len(_basic_report_issues(original, ..., bundle=bundle))`；
     - `typesafe_decisions._selection_pool(repaired) is not None`。
   - 不接受时保留原报告，`audit["repair_rejected"] = True`，不做第二次审计。
   - 接受时照现有逻辑更新 `writers`、`synthesis` 并复审一次。最多修复一轮（现状已是）。

### WP-7 复盘里的假设判定改由代码结算

目标：复盘第 4、5 节的「假设是否符合」不再由模型判断，由代码按比分结算后注入。

1. **新模块 `bot/hypothesis_settle.py`**：把 `scripts/backtest_hypotheses.py` 里的 `settle_home`、`pnl`、`Tally`、`settle_trigger` **原样移入**（不改逻辑）。
   `scripts/backtest_hypotheses.py` 改为 `from bot.hypothesis_settle import settle_home, pnl, Tally, settle_trigger`，保证脚本对外名字不变
   （`scripts/build_hypothesis_stats.py` 通过 `bt.Tally`、`bt.settle_trigger` 引用，必须继续可用）。
2. 同模块新增：

   ```python
   def settlement_block(csv_text: str, league: str, score: tuple[int, int]) -> str
   ```

   - `facts = market_facts.build_facts(market_facts.rows_from_csv(csv_text), league)`；`triggers = hypotheses.evaluate(facts)`。
   - 对每个 trigger 调 `settle_trigger(t, facts, score)`：返回 `None` → 「无法结算」；结果 >0 → 「符合」；<0 → 「不符合」；=0 → 「走盘」。
   - 输出：

     ```
     ### 假设结算（代码按比分计算）
     | 假设 | 状态 | 预测 | 结算 |
     |------|------|------|------|
     | H-M07 | 观察中 | 下盘 | 不符合 |
     ```

     状态取 `hypotheses.registry_status()`；没有触发任何假设时写「本场未触发可机械判定的假设」。
   - 任何异常返回空串并记一条 warning（不能阻断复盘）。

### WP-8 登记表「后样本」统计可在服务器一键跑

背景：登记表的「后」列由 `scripts/build_hypothesis_stats.py` 从盘口库加比分缓存机械统计，**与复盘报告无关**，这个设计保持不变。
现在的问题只是它要人在有数据的机器上手动跑两个脚本。

1. **修比分缓存的陈旧问题**（`scripts/backtest_hypotheses.py` 的 `cmd_scores`）：现在某天的缓存文件一旦存在就永不重取，
   如果取数时当天比赛没踢完，这些比赛永远没有比分。改为：缓存文件存在、但其中有状态不在 `("FT","AET","PEN","CANC","PST","ABD","AWD","WO")` 的条目，
   且该日期距今不超过 7 天 → 重取。
2. **把 `cmd_scores` 的取数主体抽成可调用函数** `fetch_scores(paths, table="fixtures") -> int`（返回新取的天数），`cmd_scores` 调它。

   - `scripts/` 不是包：在命令处理函数里用 `sys.path` 临时加入 `scripts` 目录后 import（参照 `build_hypothesis_stats.py` 文件头的做法）。

### WP-9 进度、日志与文案（原并发方案第 5 项）

1. **耗时日志**（`bot/llm_client.py`）：`_limited_stream` 与 `_limited_chat` 在请求结束时各记一条 INFO：

   ```
   LLM耗时 group=cpa_gpt endpoint=CPA-GPT model=gpt-6-astra queue=12s first=21s total=438s ok=True
   ```

   - `queue`：等组名额的秒数；`first`：拿到名额到第一个 `delta` 的秒数（非流式写 `-`）；`total`：拿到名额到结束。
   - `model` 取 `payload.get("model")`。`ok`：流式以是否出现 `done` 事件为准。
   - 不受并发上限约束的请求（`limited=False`）不记，避免走地每分钟刷日志。
2. **全模型进度**：`run()` / `run_review()` 在审计开始、修复开始时各调一次 `progress("audit", None)`、`progress("repair", None)`
   （复盘用 `review_audit`、`review_repair`）。`tgbot` 的 `on_progress` 据此把审计行置为 🔄、修复时显示「🛠 修复中」。
   `_run_multi_review` 的两个进度回调同样处理。未知 kind 仍然忽略。
3. **预计时间**：`_run_multi_sop` 的标题加「约 10~20 分钟」，`_run_multi_review` 加「两步合计约 20~40 分钟」。
4. **审计结果直接告诉用户**：`_run_multi_sop` / `_run_multi_review` 发报告前，若 `summary["audit"]` 未通过，
   先发一条 `⚠️ 审计未通过：N 项阻断问题（详见报告末尾的执行记录）`；有 `repair_rejected` 时加「修复稿未通过验收，以下为原稿」。
5. **过期文案**：`_cmd_analyze` 预览消息里全模型那句，改为
   `🧪 全模型交叉精算 = 按职责调用所选模型分别分析，再合并并独立审计（管理员功能；耗时约 10~20 分钟）。`
